### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |

|NFR-2|**Производительность**: Кэширование списка ставок в Redis с TTL 1 час для снижения нагрузки на БД|
|NFR-3|**Производительность**: Генерация CSV-файла для партнёрского КЦ не должна превышать 10 секунд|

|NFR-5|**Надежность**: При недоступности Сервиса депозитов система внутреннего КЦ должна показывать данные из локального кэша|
|NFR-6|**Надежность**: Файл для партнёрского КЦ должен генерироваться даже при частичной недоступности данных (базовые ставки)|
|NFR-7|**Надежность**: Хранение последних 5 версий файлов на SFTP-сервере для аудита и восстановления|
|NFR-8|**Безопасность**: SFTP-подключение с аутентификацией по ключам|
|NFR-9|**Безопасность**: Партнёрский КЦ имеет read-only доступ к SFTP-директории|
|NFR-10|**Безопасность**: API ставок для внутреннего КЦ использует API-key аутентификацию|
|NFR-11|**Поддерживаемость**: Формат CSV-файла должен быть документирован и согласован с партнёрским КЦ|
|NFR-12|**Поддерживаемость**: Логирование всех операций экспорта файлов и API-запросов|
|NFR-13|**Поддерживаемость**: Мониторинг успешности генерации и доставки файлов на SFTP|
|NFR-14|**Поддерживаемость**: Алерты при сбоях генерации файлов или недоступности SFTP|
|NFR-15|**Масштабируемость**: Решение должно поддерживать добавление новых партнёрских каналов в будущем|
|NFR-16|**Usability**: API ставок должен возвращать данные в JSON с понятной структурой|
|NFR-17|**Ограничения**: Партнёрский КЦ не может выполнять API-вызовы, только файловый обмен|
|NFR-18|**Актуальность**: CSV-файл должен обновляться при каждом изменении ставок в АБС|

### **Решение**

**Диаграммы:**
- [Диаграмма контекста](./Task4/C4_Context_Diagram.png)
- [Диаграмма компонентов](./Task4/C4_Component_Diagram.png)

**Ключевые архитектурные решения:**

1. **REST API в Сервисе депозитов для внутреннего КЦ**
   - Эндпоинт GET /api/rates - возвращает список всех актуальных ставок
   - Эндпоинт GET /api/rates/{depositId} - детали конкретного депозита
   - Кэширование ответов в Redis с TTL 1 час
   - API-key аутентификация для системы кол-центра
   - Поддержка фильтрации по типу депозита, сроку

2. **Модуль экспорта файлов в Сервисе депозитов**
   - Event-driven экспорт при получении события RatesUpdated из Kafka
   - Генерация CSV-файла с актуальными ставками
   - Формат: deposit_rates.csv (актуальный файл) + deposit_rates_YYYYMMDD_HHmmss.csv (архив)
   - Загрузка файла на SFTP-сервер
   - Хранение последних 5 версий файлов для аудита

3. **SFTP-сервер для обмена файлами**
   - Выделенный SFTP-сервер в DMZ
   - Отдельная директория для партнёрского КЦ
   - Аутентификация по SSH-ключам
   - Read-only доступ для партнёрского КЦ
   - Write доступ для Сервиса депозитов

4. **Синхронизация ставок через Kafka**
   - АБС публикует события "RatesUpdated" при изменении ставок
   - Сервис депозитов подписан на эти события
   - Автоматическое обновление данных в PostgreSQL
   - Инвалидация кэша в Redis при обновлении

5. **Интеграция системы внутреннего КЦ**
   - Новый модуль "Справочник депозитов" в системе КЦ
   - Интеграция через REST API с Сервисом депозитов
   - Локальное кэширование на 1 час для отказоустойчивости
   - Fallback на кэш при недоступности API

**Логика принятия решений:**

**1. Почему API для внутреннего КЦ, а не прямой доступ к БД?**
- Система КЦ уже имеет микросервисную архитектуру на Java Spring Boot
- API обеспечивает слабую связанность систем
- Возможность кэширования
- Централизованное управление доступом к данным
- Избегаем прямых запросов к PostgreSQL Сервиса депозитов

**2. Почему SFTP для партнёрского КЦ, а не API?**
- Требование заказчика - партнёрский КЦ не может делать API-вызовы (NFR-17)
- SFTP - стандартный протокол для B2B-интеграций
- Высокая безопасность при передаче данных
- Простота реализации со стороны партнёра
- Минимальные требования к инфраструктуре партнёра

**3. Почему event-driven экспорт файла для партнёрского КЦ?**
- Партнёрский КЦ всегда получает актуальные ставки
- Минимальная задержка при изменении ставок (только время импорта у партнёра)
- Используется уже существующий event от АБС через Kafka
- Партнёр забирает файл по своему расписанию (например, каждый час)
- Снижается риск консультирования по неактуальным ставкам

**4. Почему CSV формат, а не JSON или XML?**
- Простота импорта для партнёра (Excel, базы данных)
- Минимальный размер файла
- Стандартный формат для обмена табличными данными
- Легкость валидации и отладки

**5. Почему кэширование на двух уровнях (Redis + локальный кэш КЦ)?**
- Redis - централизованный кэш для всех потребителей
- Локальный кэш в системе КЦ - для отказоустойчивости
- При недоступности Сервиса депозитов операторы продолжают работать
- Graceful degradation - требование NFR-5

**6. Почему Kafka для синхронизации ставок?**
- Kafka уже используется в архитектуре MVP
- Event-driven подход - АБС остается master системой
- Асинхронная синхронизация не нагружает АБС
- Возможность подписки других систем на события о ставках

**Команды, участвующие в разработке:**

1. **Управление IT (Сервис депозитов):**
   - Разработка REST API для получения ставок
   - Разработка модуля экспорта CSV-файлов
   - Интеграция с SFTP-сервером
   - Настройка scheduled jobs

2. **Команда системы кол-центра (5 чел подрядчик):**
   - Разработка модуля "Справочник депозитов"
   - Интеграция с API Сервиса депозитов
   - Реализация локального кэширования
   - UI для отображения ставок операторам

3. **Команда инфраструктуры:**
   - Развертывание и настройка SFTP-сервера
   - Настройка SSH-ключей для аутентификации
   - Настройка файрволов и сетевых политик

4. **Партнёрский кол-центр:**
   - Разработка процесса импорта CSV-файлов
   - Настройка SFTP-клиента
   - Обновление скриптов для операторов

### **Альтернативы**

**Альтернатива 1: Email-рассылка файлов вместо SFTP**

Отправка CSV-файла на email партнёрского КЦ ежедневно.

*Преимущества:*
- Проще в реализации
- Не требует SFTP-сервера
- Привычный канал коммуникации

*Недостатки:*
- Низкая безопасность - файл в открытом виде
- Невозможность автоматизации получения у партнёра
- Зависимость от почтовых серверов
- Сложность мониторинга доставки

*Почему отклонено:* Не соответствует требованиям безопасности (NFR-8, NFR-9), сложность автоматизации

**Альтернатива 2: Предоставление веб-портала для партнёрского КЦ**

Создать отдельный веб-интерфейс, где партнёрский КЦ может просматривать ставки.

*Преимущества:*
- Актуальные данные в реальном времени
- Не нужен SFTP-сервер
- Удобный UI

*Недостатки:*
- Требует разработки и поддержки отдельного портала
- Партнёрский КЦ должен интегрировать портал в свой процесс
- Необходимость управления доступами и аутентификацией пользователей
- Не вписывается в существующие процессы партнёра

*Почему отклонено:* Слишком сложное решение для MVP, партнёр не готов менять процессы, требует дополнительных ресурсов

**Альтернатива 3: Прямой доступ партнёрского КЦ к API**

Предоставить партнёрскому КЦ API-доступ к Сервису депозитов.

*Преимущества:*
- Актуальные данные в реальном времени
- Единый API для всех потребителей
- Меньше компонентов

*Недостатки:*
- Партнёрский КЦ не может делать API-вызовы (жесткое ограничение NFR-17)
- Необходимость открывать API во внешний контур
- Риски безопасности
- Зависимость партнёра от доступности API

*Почему отклонено:* Прямое противоречие требованию NFR-17, партнёр не имеет технической возможности

**Альтернатива 4: Синхронное обновление ставок в системе КЦ при изменении в АБС**

Система КЦ подписывается на Kafka события напрямую и обновляет свою БД в реальном времени.

*Преимущества:*
- Актуальные данные без задержки
- Не нужен API-вызов при каждом запросе

*Недостатки:*
- Усложнение архитектуры системы КЦ
- Дублирование данных в БД системы КЦ
- Необходимость поддерживать синхронизацию
- Система КЦ становится зависимой от Kafka

*Почему отклонено:* Избыточная сложность, API с кэшированием достаточно для требуемой производительности (NFR-1)

### **Недостатки, ограничения, риски**

#### Недостатки решения:

1. **Дополнительная инфраструктура**
   - SFTP-сервер требует поддержки и мониторинга
   - Дополнительные затраты на инфраструктуру
   - Необходимость управления SSH-ключами

2. **Зависимость от событий Kafka**
   - Генерация файла зависит от получения события из Kafka
   - При сбое Kafka или задержке событий файл не обновится
   - Необходим мониторинг Kafka и механизм повторных попыток

3. **Ручной процесс у партнёра**
   - Партнёр должен самостоятельно забирать файл
   - Необходимость обучения персонала партнёра
   - Зависимость от действий партнёра

#### Ограничения:

1. **Партнёрский КЦ - только файловый обмен**
   - Невозможность real-time интеграции с партнёром
   - Ограниченные возможности автоматизации со стороны партнёра
   - Задержка в актуализации данных

2. **Ставки меняются централизованно в АБС**
   - Сервис депозитов не является master системой для ставок
   - Зависимость от скорости публикации событий из АБС
   - Требуется синхронизация через Kafka

3. **Система КЦ на платформе подрядчика**
   - Ограниченные возможности кастомизации
   - Зависимость от подрядчика для доработок
   - Необходимость согласования изменений

4. **MVP - базовый функционал**
   - Нет расширенной аналитики для операторов
   - Отсутствие истории изменения ставок
   - Нет персонализированных ставок для партнёрского КЦ

#### Риски:

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| **SFTP-сервер недоступен в момент генерации файла** | Средняя | Высокое | Retry механизм с экспоненциальной задержкой, мониторинг, алерты, хранение файлов локально до успешной отправки |
| **Партнёр не забирает файл вовремя** | Средняя | Среднее | Мониторинг факта скачивания файла, уведомление партнёра, процесс эскалации |
| **Ошибка при генерации CSV-файла** | Низкая | Высокое | Валидация данных перед генерацией, логирование, алерты, резервная копия предыдущего файла |
| **Система КЦ не может интегрировать API** | Низкая | Критичное | Привлечение подрядчика на ранней стадии, прототипирование интеграции, контрактные обязательства |
| **Изменение формата файла нарушает импорт у партнёра** | Средняя | Высокое | Версионирование формата, предварительное согласование изменений |
| **Задержка событий в Kafka** | Средняя | Среднее | Мониторинг в Kafka, алерты, увеличение ресурсов Kafka при необходимости |
| **Неактуальные данные в кэше Redis** | Средняя | Среднее | TTL 1 час, инвалидация кэша при получении событий об обновлении, мониторинг актуальности |
| **Партнёрский КЦ консультирует по неактуальным ставкам** | Средняя | Среднее | CSV обновляется по событию, партнёр импортирует файл по расписанию (например, каждый час), указание даты/времени актуальности в файле |

**Критичные риски требующие немедленного внимания:**
1. Перегрузка КЦ - требуется нагрузочное тестирование
2. Задержки в Kafka - требуется мониторинг и настройка алертов
3. Интеграция системы КЦ - требуется раннее привлечение подрядчика

**Общий вывод:**
Предложенное решение обеспечивает доступ к актуальным ставкам по депозитам для обоих кол-центров с учетом их технических ограничений. Для внутреннего КЦ используется современный API-подход с кэшированием, для партнёрского КЦ - проверенный файловый обмен через SFTP. Решение интегрируется с архитектурой MVP и использует существующие компоненты (Kafka, Сервис депозитов), минимизируя дополнительную сложность.
