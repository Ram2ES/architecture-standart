### <a name="_qmphm5d6rvi3"></a>**Решение**

**Диаграммы:**
- [Диаграмма контекста](./Task3/C4_Context_Diagram.png)
- [Диаграмма контейнеров](./Task3/C4_Container_Diagram.png)

**Ключевые архитектурные решения:**

1. **Новый микросервис "Сервис депозитов"** (Java Spring Boot + PostgreSQL + Redis + Kafka)
   - Центральный компонент для всей логики работы с депозитами
   - Независимое развертывание и масштабирование
   - Современный технологический стек, совместимый с существующей экспертизой
   - Избегаем доработок legacy-ядра интернет-банка подрядчиком

2. **Асинхронная интеграция с АБС через Kafka**
   - Снижение нагрузки на перегруженную БД АБС
   - Гарантия доставки сообщений (заявки не теряются)
   - Возможность обработки пиковых нагрузок
   - Развязка систем по времени

3. **Многоуровневое кэширование (Redis)**
   - Кэш ставок депозитов (обновление раз в день или по событию)
   - Кэш справочных данных (решение текущей проблемы загрузки >1 сек)
   - Персонализированные ставки с TTL
   - Достижение целевого времени отклика

4. **Расширение АБС новыми компонентами**
   - API Layer для интеграций (PL/SQL процедуры)
   - Rates Management модуль (замена Excel)
   - Queue Consumer для обработки заявок из Kafka
   - Notification Service для отправки СМС

5. **Сохранение существующих систем**
   - Интернет-банк остается монолитом (минимальные изменения)
   - СМС-подтверждение через существующий модуль
   - Сайт - минимальные изменения в backend
   - Система кол-центра - API интеграции

**Логика принятия решений:**

**1. Почему микросервис, а не монолит?**
- Требование избежать доработок ядра интернет-банка подрядчиком (NFR-11)
- Независимое масштабирование под растущую нагрузку
- Быстрая разработка силами команды банка (S6)
- Возможность использовать современные технологии (Kafka) несовместимые с .NET 4.5
- Модульность для будущего использования в кредитах (S8)

**2. Почему Kafka, а не прямой API к АБС?**
- БД АБС уже перегружена (R3, P2)
- Асинхронность не блокирует пользователя (P5)
- Гарантия доставки заявок (R5)
- Сглаживание пиковых нагрузок
- Event-driven архитектура - стандарт индустрии (S4)

**3. Почему Redis для кэша?**
- Требование времени отклика < 1сек (P1)
- Существующая проблема загрузки справочников > 1 сек (F9)
- Снижение нагрузки на БД
- In-memory storage для частых запросов ставок
- Поддержка TTL для автоматической инвалидации

**4. Почему Java Spring Boot для микросервиса?**
- Совместимость с системой кол-центра (уже на Java) (S2)
- Экспертиза в команде АБС - есть Java-специалисты (S2)
- Широкая экосистема для микросервисов
- Хорошая интеграция с Kafka, PostgreSQL, Redis
- Совместимость с существующими платформами

**5. Почему PostgreSQL для нового сервиса?**
- Совместимость с системой кол-центра (S1)
- Меньшая стоимость лицензий vs Oracle
- Хорошая поддержка JSON для гибких схем
- Горизонтальное масштабирование (в отличие от Oracle АБС)

**6. Почему расширение АБС, а не замена?**
- АБС - критичная система, рискованно менять
- Большой объем legacy-кода и бизнес-логики
- Ограниченные ресурсы MVP (6 месяцев) (+R8, +R9)
- Используем сильные стороны АБС (учет, транзакции)
- В дальнейшем можно будет рассмотреть плавный перенос функционала в микросервисы

**Команды, участвующие в разработке:**

1. **Управление IT (10 чел внутри банка):**
   - Разработка Сервиса депозитов (Java)
   - Интеграция с Kafka
   - Redis setup и конфигурация

2. **Команда АБС (20 чел):**
   - Разработка API Layer (PL/SQL)
   - Модуль управления ставками
   - Queue Consumer
   - Расширение Notification Service

3. **Команда интернет-банка (10 чел внутри + 10 подрядчик):**
   - Минимальные изменения frontend (добавление раздела депозитов)
   - Интеграция с Сервисом депозитов через REST API
   - Использование существующего СМС-модуля

4. **Команда сайта (внутри Управления IT):**
   - Добавление раздела депозитов
   - Форма подачи заявки
   - Интеграция с Сервисом депозитов

5. **Команда кол-центра (5 чел подрядчик):**
   - API для получения заявок с сайта
   - Интеграция с АБС для создания заявок

6. **Команда цифровой трансформации (10 чел):**
   - Общая координация
   - Архитектурный надзор
   - Управление интеграциями

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

**Альтернатива 1: Полная переработка интернет-банка на микросервисы**

Вместо создания отдельного Сервиса депозитов перевести весь интернет-банк на современную архитектуру.

*Недостатки:*
- Слишком рискованно для MVP
- Не укладывается в 6 месяцев
- Требует значительных ресурсов
- Зависимость от подрядчика
- Высокий риск регрессии существующего функционала

*Почему отклонено:* Не соответствует ограничениям MVP по срокам и ресурсам (+R8, +R9)

**Альтернатива 2: Прямая синхронная интеграция интернет-банка с АБС**

Добавить API в АБС и вызывать его синхронно из интернет-банка без промежуточного сервиса.

*Преимущества:*
- Более простая архитектура
- Меньше компонентов для поддержки

*Недостатки:*
- БД АБС уже перегружена - добавление нагрузки критично (R3, P2)
- Нет кэширования - не достичь целевого времени отклика (P1)
- Блокирующие вызовы ухудшат UX
- Нет буферизации пиковых нагрузок
- Высокая связанность систем

*Почему отклонено:* Прямо противоречит ключевому требованию R3 "Избежание прямой работы интернет-банка с API АБС"

**Альтернатива 3: Использование RabbitMQ вместо Kafka**

RabbitMQ - более простая альтернатива Kafka для очередей сообщений.

*Преимущества:*
- Проще в настройке и эксплуатации
- Меньше требований к ресурсам

*Недостатки:*
- Хуже масштабируется под большие нагрузки
- Нет экспертизы в команде

*Почему отклонено:* Kafka - стратегический выбор "на перспективу" согласно требованию S4.

**Альтернатива 4: Хранение ставок в микросервисе без синхронизации с АБС**

Полностью перенести управление ставками из АБС в Сервис депозитов.

*Преимущества:*
- Меньше сложности интеграции
- Независимость от АБС

*Недостатки:*
- Дублирование данных
- Несогласованность между системами
- Бэк-офис привык работать в АБС
- Нарушение единого источника истины

*Почему отклонено:* АБС должна оставаться мастер системой для критичных данных (ставки, депозиты, операции)

### **Недостатки, ограничения, риски**

#### Недостатки решения:

1. **Увеличение сложности архитектуры**
   - Добавляется новый микросервис, что требует дополнительных навыков DevOps
   - Управление консистентностью данных между системами
   - Необходимость мониторинга большего количества компонентов

2. **Асинхронность усложняет UX**
   - Клиент не получает мгновенного ответа о результате обработки заявки
   - Необходимость реализации polling или websockets для статуса
   - Сложности с обработкой ошибок и откатов

3. **Дополнительная инфраструктура**
   - Kafka cluster требует выделенных ресурсов и экспертизы
   - Redis cluster для высокой доступности
   - Дополнительные затраты на лицензии PostgreSQL

4. **Зависимость от внешних компонентов**
   - Kafka становится критичной точкой отказа
   - Redis - потеря кэша приводит к нагрузке на БД
   - Необходимость отказоустойчивых конфигураций

#### Ограничения:

1. **MVP - ручная обработка заявок бэк-офисом**
   - На этапе MVP не достигается полная автоматизация
   - Бэк-офис остается узким местом (50 человек)
   - Время обработки заявки все еще зависит от человека

2. **Сохранение legacy-систем**
   - Интернет-банк остается на устаревшем .NET 4.5
   - АБС на Delphi/Oracle не модернизируется
   - Технический долг не устраняется, а откладывается

3. **АБС не масштабируется горизонтально**
   - Ограничение Oracle БД (+R4)
   - При росте нагрузки потребуется дорогостоящее вертикальное масштабирование
   - Kafka лишь смягчает, но не решает проблему

4. **Неполная реализация персонализации**
   - Расчет персональных ставок упрощен для MVP
   - Нет сложной аналитики и ML
   - Ограниченные правила персонализации

#### Риски:

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| **Команда не успевает разработать за 6 месяцев** | Высокая | Критичное | Приоритизация функций, возможность урезать scope MVP, привлечение дополнительных ресурсов |
| **Kafka cluster нестабильно работает** | Средняя | Высокое | Квалифицированный DevOps, managed Kafka в облаке, резервное копирование, тщательное тестирование |
| **Производительность АБС деградирует** | Средняя | Критичное | Load testing, постепенное увеличение нагрузки, мониторинг, готовность к вертикальному масштабированию Oracle |
| **Несогласованность данных между системами** | Средняя | Высокое | Event sourcing, компенсирующие транзакции, регулярная сверка данных, алерты при расхождениях |
| **Интеграции между системами работают нестабильно** | Средняя | Высокое | Тщательное тестирование, retry policy, circuit breakers, мониторинг интеграций |
| **Redis падает - вся нагрузка на БД** | Средняя | Среднее | Redis cluster с репликацией, graceful degradation (работа без кэша), rate limiting |
| **Подрядчик интернет-банка не хочет вносить изменения** | Низкая | Среднее | Контрактные обязательства, минимизация изменений в ядре |
| **Бэк-офис не справляется с потоком заявок** | Высокая | Среднее | Постепенный запуск, ограничение количества заявок в день, найм временных сотрудников, приоритизация автоматизации в следующих релизах |
| **Клиенты не принимают асинхронную модель** | Средняя | Среднее | UX-тестирование, понятные сообщения о статусе, push-уведомления, возможность отслеживания статуса |
| **Требования регуляторов изменяются** | Низкая | Критичное | Мониторинг изменений законодательства, гибкая архитектура, возможность быстрого внесения изменений |

**Критичные риски требующие немедленного внимания:**
1. Успеть за 6 месяцев - требуется жесткое управление
2. Производительность АБС - требуется нагрузочное тестирование на ранних этапах
3. Стабильность Kafka - требуется выделенная команда DevOps

**Общий вывод:**
Предложенное решение представляет собой баланс между инновациями и легаси. Мы вводим современные практики (микросервисы, event-driven, кэширование) там, где это дает максимальную пользу, и сохраняем легаси-системы там, где их изменение слишком рискованно или дорого для MVP. Решение позволяет быстро выйти на рынок с минимальным функционалом и создает фундамент для дальнейшего развития.
